## 📌 製品の本質

**Irasse とは**:
飲食店の顧客識別と接客価値を、客の負担なく実現するSaaS。
多言語・多文化に対応し、グローバルな観光地・飲食店で使える。

**核心の DNA**:
- ✅ 外部の信頼されたサービスを活用する（自前主義を捨てる）
- ✅ Irasse は現場価値に集中する
- ✅ 識別は目的ではなく、接客価値を生む手段
- ✅ 店側UIはシンプルを最優先
- ✅ 外国人客が多いカジュアル〜中級店に寄せる
- ✅ グローバル設計（場所を選ばない）

---

## 🎯 Phase 1 のゴール

**「Irasse は本当に飲食店の役に立つ」を実証する**

具体的なゴール:
1. 普遍的な機能として実装完了（特定の店に依存しない、どの店でも使える設計）
2. 「常連が分かる」「履歴で接客が変わる」を実感してもらえる設計
3. 売上・データ分析で「いつもより役立つ」と思ってもらえる設計
4. 実証店舗（候補は複数あり得る）でリアルなデータ取得

**実証する店舗について**:
- Doobie は候補の1つ（今日デモ実施、フィードバック取得済み）
- ただし Doobie で運用するかは未確定
- 他の店舗にも営業して、最初に契約してくれた店で実証する可能性もある
- Phase 1 完成時点で、実証先を決定する

**NOT Phase 1 のゴール**:
- ❌ 完璧な機能網羅
- ❌ グローバル展開の実装
- ❌ 投資調達の実現
- ❌ 多くの店舗への拡大

---

## 👥 ターゲット

**Irasseが向いてる店**:
- 外国人客が多い、または多言語対応が必要
- カジュアル〜中級レストラン（居酒屋、バル、カフェ、定食屋）
- スタッフ少数で効率化したい
- データ駆動の接客に興味がある
- 例: Doobie Doo Bar（ホーチミン）

**Irasseが向かない店**（明確化）:
- 超高級店（懐石、寿司カウンター、フレンチ）
- 完全おまかせ・体験型の店
- 「会話・接客自体が商品」の店

### 機能2: Google Login で顧客識別

#### 客側 UI

**QR スキャン直後の画面**:
```
[{shop_name} のメニュー画面]

画面下部に控えめに:
「Save your visit?
 Next time, we'll remember your favorites and language.
 (履歴を残しますか? 次回もお気に入りと言語を覚えます)」

[Continue with Google]
[Save later (今は履歴を残さない)]
```

**Google認証フロー**:
1. [Continue with Google] タップ
2. Google ログイン画面（既ログイン済みなら1秒）
3. 「Irasse がアクセスを要求しています」
   - 取得情報: 名前、メアド（Google管理）
4. [許可] タップ
5. メニュー画面に戻る

**連携後の表示**:
```
画面上部に控えめに:
「Welcome back, [名前]さん」
「3rd visit」（来店回数）
「Last time you enjoyed: [料理名]」（前回お気に入り、あれば）
```

#### 内部処理

```typescript
// データモデル
type User = {
  id: string;              // Irasse 内部ID (UUID)
  google_id?: string;      // Google User ID
  // 将来用（Phase 2+）:
  // line_id?: string;
  // apple_id?: string;
  // zalo_id?: string;
  name: string;
  created_at: timestamp;
  last_seen_at: timestamp;
  preferred_lang: 'en' | 'ja' | 'ko' | 'zh' | 'vi';
}

// Google OAuth フロー
1. 客が [Continue with Google] タップ
2. Google OAuth で認可コード取得
3. サーバー側で Google API を呼び、user_info 取得
4. データベースで google_id で User 検索
5. 存在すれば: その User を使用
6. 存在しなければ: 新規 User 作成
7. セッションを発行（Cookie/JWT）
```

### 重要な定義: Visit / Session

**「1 visit（来店1回）」の定義**:

```
1 visit = 会計完了で1 visit

→ 同じ Google ID の客が、同じ店舗で、
  会計を完了するまでの一連の注文を 1 visit とする
```

**理由**:
- 日付を跨いだ場合（23時来店 → 1時会計）も1 visit として正確に数えられる
- Day定義（同日同店）だと、深夜またぎで誤って2 visit になる
- 店側の感覚として「会計が visit の境界」が自然

**データモデル**:
```typescript
type Session = {
  id: string;                          // UUID
  user_id?: string;                    // 連携客の場合のみ
  shop_id: string;
  table_number: number;
  started_at: timestamp;               // 最初の注文時
  ended_at?: timestamp;                // 会計完了時（active時はnull）
  total: number;                       // 累計（会計時に確定）
  status: 'active' | 'completed';
  orders: Order[];                     // このsessionの全注文
}
```

**集計ロジック**:
```typescript
// 来店回数（visit count）
visit_count = COUNT(
  sessions
  WHERE user_id = X
    AND shop_id = Y
    AND status = 'completed'
)

// 合計支出
total_spent = SUM(
  sessions.total
  WHERE user_id = X
    AND shop_id = Y
    AND status = 'completed'
)

// 最終来店日
last_visit = MAX(
  sessions.ended_at
  WHERE user_id = X
    AND shop_id = Y
    AND status = 'completed'
)

// 平均支出
avg_spent = total_spent / visit_count
```

**Sessionの遷移**:
```
状態: active
   ↓ 客が最初の注文 → Session 作成
   ↓ 追加注文 → 同じSessionに追加
   ↓ 客が会計依頼 → まだ active
   ↓ 店側で「Complete」押下 → status: 'completed', ended_at 設定

状態: completed
   → 集計対象、visit としてカウント

→ 客が次回来店時、新しい Session が始まる
```

**エッジケース**:
- 会計せずに帰った場合（行き逃げ等）: session は active のまま、店側で手動 cancel 可能
- 同日に再来店: 新しい session として開始（前 session が completed であれば 2 visits）

```

   ※ 季節・天気・競合等の影響大
📊 リピート率 25%+
```

```
✅ オーナー「これあると無いとで全然違う」
✅ スタッフ「お客さんとの会話が増えた」
✅ 客「次回もスムーズ」
✅ 同類型店3〜5店から「使いたい」と声
```

**評価方法**:
- Phase 1 終了時、必達KPI 4つのうち3つ以上達成で「成功」
- 参考KPI は付随的に達成できれば良い、達成しなくても失敗ではない

この3つを守り続ければ、Irasse は飲食店業界の常識を変えられる。
